# Live Activity contract (iOS <-> transcription worker)

The worker pushes transcription progress to an ActivityKit Live Activity over APNs, so the
lock screen / Dynamic Island keeps updating after the app is suspended, and sends a final
`end` event with an alert on completion or failure. Both sides must keep the names below
identical: ActivityKit decodes `content-state` with a plain `JSONDecoder` (no key
conversion), so a renamed key silently breaks the update.

## Flow

1. App creates the job (`POST /jobs`), then starts the activity with
   `Activity.request(attributes:content:pushType: .token)`.
2. App observes `activity.pushTokenUpdates` and upserts each token (hex string) into
   `live_activity_tokens` (table below) with the user's JWT (RLS). Tokens can change: upsert
   every time one is emitted.
3. Worker pushes `update` events at real stage transitions (and at most one in-stage progress
   push per ~20 s), then one `end` event on `done` / `failed`, then deletes the job's rows.
4. Dead tokens (HTTP 410, `BadDeviceToken`, `Unregistered`, `ExpiredToken`) are deleted by the worker.

## ActivityAttributes (static, set when the app starts the activity)

| key     | type   | meaning |
|---------|--------|---------|
| `jobId` | String | `transcription_jobs.id` (UUID). Must equal `live_activity_tokens.job_id`. |
| `name`  | String | meeting name, display only (never sent by the server) |

## ContentState (the `content-state` JSON)

| key           | type            | always present | meaning |
|---------------|-----------------|----------------|---------|
| `stage`       | String          | yes | `queued`, `preparing`, `transcribing`, `summarizing`, `done`, `failed` |
| `progress`    | Double or null  | yes | overall fraction 0.0 to 1.0; `null` = indeterminate. `done` is always 1.0 |
| `chunk`       | Int             | no  | chunks finished (chunked jobs, `transcribing`) |
| `totalChunks` | Int             | no  | total chunks |
| `message`     | String          | no  | short hint (max 120 chars), e.g. "Retrying" with `queued` |

Keys are camelCase. Absent optional keys are omitted (not `null`), except `progress`.
Unknown future keys must not break decoding (Swift ignores them by default).
`failed` never carries the raw error; the app should show its own localized text.

Stage meaning: `queued` (waiting, or re-queued for a retry), `preparing` (download /
chunk fetch / audio conversion), `transcribing`, `summarizing` (summary, overview, actions),
`done` (end event), `failed` (end event, permanent failure only; retryable errors go back to
`queued` and the activity stays alive).

Background-upload jobs (`POST /jobs` with `upload_pending=true`, see
BACKGROUND_UPLOAD_CONTRACT.md): while the job is `awaiting_upload` the server sends no push
(the app shows its own local "uploading" state; `stage` stays NULL). When the worker
promotes the job to `pending` it pushes `queued` (progress 0), then the usual
`preparing` -> `transcribing` -> `summarizing` -> `done` sequence. An upload that never
finishes (`upload_expired`) ends the activity with `failed`. The token can be registered as
soon as the app has the `job_id` from the create response, i.e. before the upload completes.

`transcription_jobs.stage` mirrors the same values (nullable; NULL = not reported yet, treat
as `queued` while `status = 'pending'`). `current_stage` stays free text for old clients.

## Swift (paste into the shared target)

```swift
import ActivityKit

struct TranscriptionActivityAttributes: ActivityAttributes {
    struct ContentState: Codable, Hashable {
        var stage: String          // queued | preparing | transcribing | summarizing | done | failed
        var progress: Double?      // 0...1, nil = indeterminate
        var chunk: Int?
        var totalChunks: Int?
        var message: String?
    }
    var jobId: String
    var name: String
}
```

(A `String` stage is deliberate: an unknown future stage still decodes. Map it to an enum
in the view with a default case.)

## Python payload example (what the worker sends)

Update, `apns-push-type: liveactivity`, `apns-priority: 5`:

```json
{"aps": {
  "timestamp": 1790000000,
  "event": "update",
  "stale-date": 1790001200,
  "content-state": {"stage": "transcribing", "progress": 0.42, "chunk": 2, "totalChunks": 4}
}}
```

End (`done`), `apns-priority: 10`:

```json
{"aps": {
  "timestamp": 1790000600,
  "event": "end",
  "dismissal-date": 1790011400,
  "content-state": {"stage": "done", "progress": 1.0},
  "alert": {"title": "Meeting ready", "body": "Your transcript and summary are ready.", "sound": "default"}
}}
```

`failed` is the same shape with `"stage": "failed"`, title "Transcription failed", body
"Open SnipNote to try again." The alert strings are plain English; the app can ignore them
by not relying on the alert and instead presenting its own local text from `stage`.
Generated by `apns.build_payload()`.

## Token upload table: `live_activity_tokens` (migration 008)

| column        | notes |
|---------------|-------|
| `job_id`      | UUID, FK `transcription_jobs(id)` ON DELETE CASCADE |
| `user_id`     | UUID, must equal `auth.uid()` |
| `token`       | hex of `Activity.pushToken` (32 to 512 hex chars; enforced) |
| `environment` | `sandbox` (debug / dev-signed builds) or `production` (TestFlight and App Store) |
| `bundle_id`   | optional; overrides the server's `APNS_BUNDLE_ID` for the `apns-topic` |
| `created_at`, `updated_at` | automatic |

Unique on `(job_id, token)`: use upsert `onConflict: "job_id,token"`. RLS: an authenticated
user can select/insert/update only rows with `user_id = auth.uid()`, and only for a job they
own (insert/update check `transcription_jobs.user_id`). The service role (worker) bypasses RLS.
Choose `environment` at build time (`#if DEBUG` = sandbox). A token sent to the wrong host
gets `BadDeviceToken` and is deleted.

## Limits

* Payload under 4 KB (ours is about 250 bytes; `message` is capped at 120 chars).
* A Live Activity lives at most 8 hours (plus up to 4 more on the lock screen after it ends);
  `dismissal-date` is at most 4 h after the end event (default 3 h).
* `stale-date` = push time + `APNS_STALE_SECONDS` (default 20 min) on every update. Long
  single-request transcriptions can go several minutes between pushes; if the state goes
  stale the app should render "still working" (`context.isStale`), not an error.
* APNs budgets priority-10 pushes; only the final `end` uses it. Updates use priority 5 and
  expire after 2 min (a newer one supersedes them).
* Pushes are best effort: the app must still reconcile with `transcription_jobs` (status,
  `stage`) when it comes to the foreground.
* `timestamp` orders events; an older timestamp than the one already shown is ignored by iOS.
